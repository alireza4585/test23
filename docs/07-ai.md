# ۱۱. برنامهٔ یکپارچه‌سازی هوش مصنوعی (AI Integration Plan)

## اصل راهنما

> **اعداد را موتور تحلیل حساب می‌کند. AI تفسیر و پیشنهاد می‌دهد. تصمیم با مدیر است.**

این تقسیم کار سه هدف دارد:

1. **دقت:** LLM هیچ عددی نمی‌سازد و فقط از دادهٔ محاسبه‌شده نقل می‌کند.
2. **کنترل هزینه:** پیشنهادهای روزانه با قواعد ساخته می‌شوند و LLM فقط هنگام گفتگو یا روایت گزارش فراخوانی می‌شود.
3. **پایداری:** اگر سرویس AI در دسترس نباشد، داشبورد، هشدار و پیشنهادها همچنان کار می‌کنند.

```
داده‌های عملیاتی ──► Analytics Engine (dailyMetrics) ──► Rule Engine (aiInsights: explainable)
        │                         │                                  │
        └──────────────► Hotel Context (فشرده، بدون PII) ◄────────────┘
                                  │
                         LlmProvider (port) ──► Claude
                                  │
          ┌───────────────────────┼─────────────────────────┐
     دستیار گفتگو           خلاصهٔ مدیریتی (n8n)         (فاز ۲) روایت insight و گزارش PDF
```

## لایه‌ها در MVP (پیاده‌سازی‌شده)

### ۱. Analytics Engine (`functions/src/analytics/metrics.ts`)

تابع خالص `computeDailyMetrics` است، با تست واحد. هر شب `dailyMetrics/{day}` را می‌سازد و شامل این شاخص‌هاست: اشغال، ADR، RevPAR، درآمد، مصرف و هزینهٔ انرژی، **برق به ازای اتاق اشغال**، اختلاف با baseline، SLA تعمیرات و میانگین زمان رفع، زمان نظافت، اقلام کم‌موجود و ارزش انبار.

### ۲. Rule Engine قابل‌توضیح (`rules-engine.ts`)

هر insight دارای `title`، `summary`، `recommendation`، `evidence[]` (چرا)، `confidence`، `priority`، `estimatedMonthlySaving` و `route` است.

| قاعده | منطق | خروجی نمونه |
|---|---|---|
| `energyIntensity` | برق به ازای اتاق اشغال در ۴ روز اخیر در برابر ۲۱ روز قبل از آن (افزایش ۱۲٪ یا بیشتر، در حالی که اشغال تقریباً ثابت مانده) | «افزایش ۲۲٪ شدت مصرف برق بدون تغییر اشغال؛ بررسی HVAC و اتاق‌های خالی» با صرفه‌جویی ماهانهٔ تخمینی |
| `stockout` | سرعت مصرف (issue و waste) ← روزهای باقی‌مانده تا اتمام (۵ روز یا کمتر) | «پیش‌بینی اتمام شامپو تا ۳ روز آینده؛ سفارش پیشنهادی» |
| `hkEfficiency` | زمان واقعی نظافت خروج در ۷ روز اخیر در برابر هدف هتل (۱۵٪ یا بیشتر بالاتر) | «زمان نظافت اتاق‌های تخلیه ۲۴٪ بیش از هدف» |
| `repeatFailure` | ۳ خرابی یا بیشتر از یک دسته در یک محل طی ۳۰ روز ← نگهداری پیشگیرانه | «۳ خرابی تکراری در اتاق ۴۰۵ طی ۳۰ روز؛ تعویض به‌جای تعمیر» |
| `outOfOrderRevenue` | اتاق‌هایی که بیش از ۲۴ ساعت خارج از سرویس‌اند × ADR | «۲ اتاق بیش از ۲۴ ساعت خارج از سرویس» و درآمد ازدست‌رفته |
| `weekdayOccupancy` | فاصلهٔ اشغال آخر هفته و روزهای میانی در ۲۸ روز اخیر | «فاصلهٔ ۹ واحدی اشغال؛ بستهٔ اقامت میان‌هفته» |

مدیر هر insight را **پذیرش، رد یا اجراشده** علامت می‌زند. این بازخورد ورودی فاز یادگیری است.

### ۳. LLM Provider Port (`ai/provider.ts`)

```ts
interface LlmProvider { complete(req: { system, messages, maxTokens? }): Promise<{ text, model, status: "ok"|"refused"|"truncated", usage }> }
```

- پیاده‌سازی فعلی: `AnthropicProvider` با SDK رسمی `@anthropic-ai/sdk`. مدل با پارامتر `AI_MODEL` تنظیم می‌شود.
- **Prompt caching:** system prompt با `cache_control` علامت‌گذاری شده است.
- **Server-side fallback** (`fallbacks: "default"`): اگر مدل اصلی درخواستی را رد کند، همان فراخوانی روی مدل جایگزین توصیه‌شده تکرار می‌شود. اگر باز هم رد شود، `status: "refused"` برمی‌گردد و کاربر پیام مؤدبانه و بومی‌شده می‌بیند.
- `effort: "medium"` برای پاسخ سریع در گفتگو. `maxRetries: 2` و timeout ۶۰ ثانیه.
- تعویض ارائه‌دهنده، مثلاً مدل self-hosted روی سرور داخلی، فقط یعنی یک کلاس جدید که همین interface را پیاده کند.

### ۴. دستیار گفتگو (`aiAssistant` callable)

1. Authorization: نقش با `ai.assistant.use` و عضویت در هتل.
2. Rate limit: ۳۰ درخواست در ساعت برای هر کاربر (`users/{uid}/usage`).
3. **Grounding:** `buildHotelContext` یک snapshot فشرده می‌سازد: KPIهای ۱۴ روز، baseline و تعرفه، وضعیت لحظه‌ای اتاق‌ها، تیکت‌های باز (سن، SLA)، اقلام کم‌موجود و insightهای فعال. **هیچ داده‌ای از مهمان یا هویت پرسنل در آن نیست.**
4. System prompt به مدل می‌گوید: فقط از `<hotel_data>` پاسخ بده؛ اول جواب مستقیم، بعد ۲ تا ۴ عدد پشتیبان و بعد اقدام مشخص؛ عدد نساز؛ فارسی با ارقام فارسی؛ حداکثر ۲۲۰ کلمه.
5. تاریخچهٔ گفتگو تا ۱۲ نوبت.
6. پاسخ همراه با `dataPoints` (اعداد کلیدی برای نمایش chip) برگردانده می‌شود. هر گفتگو در `aiConversations` با model، status و usage ثبت می‌شود.

نمونه پرسش‌ها: «چرا مصرف برق زیاد شده؟»، «کدام خرابی‌ها از SLA گذشته‌اند؟»، «برای کاهش هزینهٔ این ماه چه کنم؟»، «کدام اقلام باید امروز سفارش داده شوند؟»

### ۵. خلاصهٔ مدیریتی (`GET /v1/.../summary?narrative=fa`)

n8n هر صبح KPIها، هشدارها و insightها را می‌گیرد. LLM یک خلاصهٔ حداکثر ۱۸۰ کلمه‌ای می‌نویسد که شامل تیتر، ۳ تا ۵ عدد تصمیم‌ساز و «اولویت‌های امروز» است. اگر LLM در دسترس نباشد، `narrative: null` برمی‌گردد و گزارش فقط با جدول اعداد ارسال می‌شود.

### حالت دمو

`DemoAiAssistant` بدون هیچ API و با قواعد محلی به همان پرسش‌های نمونه پاسخ مستند می‌دهد. این حالت برای دمو فروش در محیط بدون اینترنت مناسب است.

## حاکمیت، کیفیت و هزینه

- **Human-in-the-loop:** AI هیچ تغییری در داده ایجاد نمی‌کند. فقط پیشنهاد می‌دهد و تصمیم با مدیر است. در فاز Agent هم هر اقدام تأیید لازم دارد و در audit log ثبت می‌شود.
- **ارزیابی:** مجموعه‌ای از پرسش‌های واقعی مدیران با پاسخ مرجع (golden set)، که پیش از تغییر مدل یا prompt اجرا می‌شود. معیارها: درستی عدد، استناد به داده، قابل‌اجرا بودن پیشنهاد.
- **پایش:** `aiConversations` (usage، status و نرخ refusal) و نرخ پذیرش insightها، به‌عنوان شاخص ارزش AI برای فروش.
- **هزینه:** cache system prompt، context فشرده (حدود ۲ تا ۴ هزار توکن)، سقف درخواست، و LLM فقط برای «روایت» نه برای محاسبه.
- **حریم خصوصی:** فقط داده‌های تجمیعی عملیاتی به LLM فرستاده می‌شود. در صورت الزام قانونی، provider به مدل داخلی یا self-hosted تغییر می‌کند.
- **دسترسی از ایران:** دسترسی به API ارائه‌دهندگان خارجی ممکن است محدود باشد. معماری port و fallback به قواعد این ریسک را پوشش می‌دهد (رجوع کنید به [۰۸](08-roadmap.md)).
